# ADR-001: Arquitetura do Backend em Node.js e Escopo da Fase 1 (MVP Click & Collect)

- **Status:** Aceito (*Accepted*)
- **Data:** Outubro de 2026
- **Autor:** Vinícius Ferreira Vianna
- **Contexto:** Projeto MegaLoja Online - Módulo Click & Collect

---

## 1. Contexto e Problema

A MegaLoja Online necessita de uma API RESTful leve, modular e performática para suportar o novo fluxo de *Click & Collect*. Na **Fase 1 do MVP**, o foco principal é estruturar o banco de dados relacional com dados de lojas e estoque, além de disponibilizar os dois endpoints mais críticos da jornada do cliente:

1. `GET /api/stores`: Listagem e consulta de lojas físicas com estoque disponível do item selecionado.
2. `POST /api/orders`: Criação do pedido na modalidade *Click & Collect*, realizando a reserva do estoque e gerando os códigos de retirada (QR Code e PIN).

Para garantir um desenvolvimento ágil, testável e de fácil manutenção no modelo de **monorepo**, faz-se necessário definir a arquitetura do backend em Node.js, a estrutura das pastas, a estratégia de persistência com SQLite e os esquemas de validação de payload HTTP.

---

## 2. Decisão Arquitetural

### 2.1 Padrão Arquitetural: Arquitetura em Camadas (Layered Architecture)
Adotaremos uma arquitetura organizada em camadas bem definidas e desacopladas no backend Node.js:

- **Routes / Controllers:** Responsáveis pelo recebimento das requisições HTTP, extração de parâmetros e resposta ao cliente.
- **Middlewares:** Responsáveis pela validação de schemas de entrada (payload/query) antes de atingir as regras de negócio.
- **Services (Business Rules):** Camada contendo a lógica central do *Click & Collect* (ex: verificação do estoque mínimo de 2 unidades, geração do PIN de 4 dígitos e hash do QR Code).
- **Repositories / Database:** Camada responsável pela execução de queries SQL e comunicação direta com o banco de dados SQLite.

### 2.2 Stack e Ferramentas Selecionadas
- **Runtime & Framework:** Node.js com Express.js.
- **Banco de Dados:** SQLite3 (driver `sqlite` / `sqlite3` assíncrono para execução embarcada local).
- **Validação de Schemas:** Zod (para validação estática e runtime de payloads e query strings com lançamento de erros padronizados).

## 4. Scripts SQL do SQLite (DDL & Seed Data)

### 4.1 Schema do Banco de Dados (`src/db/init.sql`)

```sql
PRAGMA foreign_keys = ON;

-- Tabela de Lojas Físicas
CREATE TABLE IF NOT EXISTS lojas (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    nome TEXT NOT NULL,
    endereco TEXT NOT NULL,
    cep TEXT NOT NULL,
    latitude REAL,
    longitude REAL,
    capacidade_pacotes INTEGER DEFAULT 100,
    ativo INTEGER DEFAULT 1
);

-- Tabela de Estoque por Loja
CREATE TABLE IF NOT EXISTS estoque_loja (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    loja_id INTEGER NOT NULL,
    produto_id TEXT NOT NULL,
    quantidade INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (loja_id) REFERENCES lojas(id) ON DELETE CASCADE,
    CONSTRAINT unq_loja_produto UNIQUE (loja_id, produto_id)
);

-- Tabela de Pedidos Click & Collect
CREATE TABLE IF NOT EXISTS pedidos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    cliente_nome TEXT NOT NULL,
    cliente_cpf TEXT NOT NULL,
    produto_id TEXT NOT NULL,
    loja_id INTEGER NOT NULL,
    modalidade_entrega TEXT NOT NULL CHECK(modalidade_entrega IN ('ENTREGA_PADRAO', 'CLICK_COLLECT')) DEFAULT 'CLICK_COLLECT',
    status TEXT NOT NULL CHECK(status IN ('PENDENTE', 'EM_SEPARACAO', 'PRONTO_PARA_RETIRADA', 'ENTREGUE', 'CANCELADO')) DEFAULT 'PENDENTE',
    codigo_pin TEXT NOT NULL,
    codigo_qr TEXT NOT NULL,
    terceiro_autorizado_nome TEXT,
    terceiro_autorizado_cpf TEXT,
    criado_em DATETIME DEFAULT CURRENT_TIMESTAMP,
    atualizado_em DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (loja_id) REFERENCES lojas(id)
);
```

## 5. Schemas de Validação de Payload com Zod

### 5.1 Schema de Validação para Pedidos (`src/schemas/orderSchema.js`)

```javascript
import { z } from 'zod';

export const createOrderSchema = z.object({
  body: z.object({
    cliente_nome: z
      .string({ required_error: 'O nome do cliente é obrigatório.' })
      .min(3, 'O nome deve ter no mínimo 3 caracteres.'),
    
    cliente_cpf: z
      .string({ required_error: 'O CPF do cliente é obrigatório.' })
      .regex(/^\d{11}$/, 'O CPF deve conter exatamente 11 dígitos numéricos.'),
    
    produto_id: z
      .string({ required_error: 'O ID do produto é obrigatório.' })
      .min(1, 'Identificador do produto inválido.'),
    
    loja_id: z
      .number({ required_error: 'O ID da loja é obrigatório.' })
      .int()
      .positive('O ID da loja deve ser um número inteiro positivo.'),
    
    modalidade_entrega: z
      .enum(['CLICK_COLLECT', 'ENTREGA_PADRAO'], {
        invalid_type_error: 'Modalidade de entrega inválida.',
      })
      .default('CLICK_COLLECT'),
    
    terceiro_autorizado_nome: z.string().optional(),
    terceiro_autorizado_cpf: z
      .string()
      .regex(/^\d{11}$/, 'O CPF do terceiro autorizado deve conter 11 dígitos numéricos.')
      .optional(),
  }),
});
```

### 5.2 Schema de Validação para Consulta de Lojas (`src/schemas/storeSchema.js`)

```javascript
import { z } from 'zod';

export const getStoresSchema = z.object({
  query: z.object({
    cep: z
      .string({ required_error: 'O CEP é obrigatório para consultar lojas.' })
      .regex(/^\d{5}-?\d{3}$/, 'Formato de CEP inválido (Ex: 90020-000 ou 90020000).'),
    
    produto_id: z
      .string({ required_error: 'O ID do produto é obrigatório para verificar o estoque.' })
      .min(1, 'Identificador do produto inválido.'),
  }),
});
```

### 5.3 Middleware Genérico de Validação (`src/middlewares/validateRequest.js`)

```javascript
export const validateRequest = (schema) => async (req, res, next) => {
  try {
    await schema.parseAsync({
      body: req.body,
      query: req.query,
      params: req.params,
    });
    return next();
  } catch (error) {
    return res.status(400).json({
      status: 'error',
      message: 'Falha na validação dos dados de entrada.',
      errors: error.errors.map((err) => ({
        field: err.path.join('.'),
        message: err.message,
      })),
    });
  }
};
```

## 6. Consequências e Benefícios

- **Padronização:** A adoção da *Layered Architecture* garante separação clara de responsabilidades entre regras de negócio, infraestrutura de banco e APIs.
- **Qualidade dos Dados:** O uso do Zod intercepta requisições malformadas antes de acionar a camada de banco de dados.
- **Portabilidade no Monorepo:** O SQLite embarcado permite que qualquer desenvolvedor clone o repositório e rode o backend sem instalar serviços adicionais como Docker ou SGBDs dedicados.
- **Próximos Passos (Fase 2):** Implementação dos serviços do Painel Administrativo para alteração de status (`PATCH /api/admin/orders/:id/status`) e endpoint de validação por bipagem de QR Code (`POST /api/admin/orders/validate`).
